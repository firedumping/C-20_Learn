## 3. 对象生命周期与所有权

### 必须能回答

1. 这个对象是谁创建的？
2. 谁负责销毁？
3. 被引用或借用的对象至少活到什么时候？
4. 操作抛异常时，资源是否仍会释放？
5. 对象被移动后处于什么状态？
6. 回调保存的是引用、指针、`string_view`，还是拥有所有权的值？

### 常见错误

- 用 `std::string_view` 保存临时字符串的内容。
- 用 `std::span` 访问已经销毁的容器。
- 在回调队列中保存局部对象引用。
- 多个地方都认为自己拥有资源，导致重复释放。
- 为了避免思考所有权而到处使用 `shared_ptr`。
- 在析构、关闭或异常路径中只处理“成功路径”。

### 复习实验

#### 实验 A：回调生命周期

构造一个保存 `std::function<void()>` 的队列。分别测试：

1. 按值捕获字符串。
2. 捕获局部字符串的引用。
3. 捕获 `string_view`。
4. 对象离开作用域后再执行任务。

使用 ASan 验证悬空访问。写下为什么任务队列通常应拥有回调所需的数据。

#### 实验 B：异常下的资源释放

写一个 RAII 包装器，管理文件描述符或文件对象。让第二个操作抛出异常，验证资源仍被释放。把析构函数改成不释放资源，观察泄漏检查结果。

#### 实验 C：移动后的状态

对一个自己实现的 `MoveOnlyBuffer` 执行：

- 移动构造。
- 移动赋值。
- 自移动。
- 移动后再次析构。

验收标准不是“程序碰巧没崩溃”，而是对象始终满足声明的不变量。

## 4. 并发基础

### 先定义不变量

不要先问“要不要加锁”，先回答：

- 哪些状态会被多个线程访问？
- 哪些操作必须在一次临界区内完成？
- 哪个线程拥有对象？
- 线程如何开始、停止和加入？
- 队列满时发生什么？
- 关闭时剩余任务怎么处理？

### 数据竞争与逻辑竞争

数据竞争是缺少同步的并发读写，属于未定义行为。逻辑竞争是即使没有未定义行为，结果仍依赖线程执行顺序。

加锁能消除数据竞争，但不会自动消除逻辑竞争。例如两个请求都读取当前余额后再扣款，即使每次读写都有锁，也可能扣错。

### 常见错误

- 用“运行一百次没出错”证明线程安全。
- 持锁调用未知回调，造成死锁或长时间阻塞。
- 条件变量没用谓词，无法正确处理虚假唤醒。
- 关闭时只设置标志，却不唤醒等待线程。
- 原子变量保护单个字段，却无法保护多个字段组成的不变量。
- 无限重试或无限队列导致资源耗尽。

2. 完成 `docs/12` 的有界队列，并补充关闭后仍能消费剩余任务的行为。

## 5. 事件循环

### 核心模型

单线程事件循环通常包含：

```text
事件源
  ├── IO 可读/可写
  ├── 定时器到期
  ├── 系统信号或退出请求
  └── 其他模块投递的任务
           │
           ▼
     就绪任务队列
           │
           ▼
   Run One Tick：执行当前批次
           │
           ▼
   更新定时器和统计信息
```

单线程不等于系统中永远只有一个线程。真实项目常有 IO 线程、工作线程和 UI 线程，但关键状态应由明确的线程所有者管理。

### 单线程事件循环的优势

- 共享状态天然串行访问，减少锁。
- 任务顺序更容易推理。
- 回调执行线程固定，降低对象生命周期风险。
- 日志和性能指标更容易关联。

### 代价与风险

- 一个慢回调会阻塞所有后续任务。
- 高优先级任务过多会造成普通任务饥饿。
- 重入和回调中再次投递任务需要明确规则。
- CPU 密集工作应放到独立工作线程，而不是长期占用事件循环。
- 如果队列无界，过载会变成内存持续增长。

### 必须定义的行为

1. `post` 在停止后返回什么？
2. 队列满时阻塞、拒绝还是丢弃？
3. 高优先级任务是否按 FIFO 保持同优先级顺序？
4. 回调中投递的新任务在同一轮还是下一轮执行？
5. 关闭时是否执行剩余任务？
6. 定时器到期顺序和相同截止时间的顺序是什么？
7. 异常从任务中抛出时，事件循环继续还是终止？

### 最小伪代码

```cpp
while (!stop_requested) {
    move_due_timers_to_ready_queue();

    auto batch = take_current_ready_batch();
    for (auto& task : batch) {
        try {
            task.callback();
        } catch (const std::exception& error) {
            report_task_error(error);
        }
    }

    wait_until_next_timer_or_new_event();
}
```

这里故意把本轮任务取成批次。回调中产生的新任务在下一轮执行，可以避免某些无限重入。其他产品可能有不同语义，关键是固定并测试。

## 6. Linux 与操作系统基础

### 进程、线程与系统调用

- 进程拥有独立虚拟地址空间和资源。
- 线程共享进程地址空间中的大部分内容和文件描述符。
- 系统调用是从用户态进入内核态的受控入口。
- 阻塞调用会让线程进入等待状态，并不等于 CPU 持续空转。
- 非阻塞 IO 返回“暂时不可用”，通常和事件通知机制一起使用。

### 文件描述符

Linux 中许多资源都通过文件描述符访问，包括文件、管道、套接字和设备。

必须掌握：

- 文件描述符泄漏如何观察。
- `read` 返回 0、正数和 -1 分别意味着什么。
- 为什么一次 `read` 不代表读到完整业务消息。
- 进程退出或崩溃后资源如何回收。

### IPC 与等待

知道以下机制解决什么问题即可：

- pipe / FIFO：简单字节流通信。
- Unix domain socket：本机进程通信，支持流或数据报。
- shared memory：低拷贝共享数据，但同步责任更重。
- message queue：消息边界和排队。
- eventfd：事件通知。
- `epoll`：等待多个 FD 的事件，适合 Linux 事件驱动服务。

不要在项目 MVP 中为了“技术丰富”全部使用。设备通信使用串口、TCP 或虚拟传输即可。

### 虚拟内存

必须能解释：

- 虚拟地址为什么存在。
- 页面、缺页和内存映射的基本含义。
- 为什么 `malloc` 成功不代表物理内存已经全部占用。
- 为什么内存泄漏最终会造成 OOM 或系统抖动。
- 线程栈和堆的常见区别。

### 信号

信号处理函数中只能执行非常有限的安全操作。一般应通过管道、`eventfd` 或自管道把信号转成事件循环中的普通任务，而不是在信号处理函数中做复杂工作。

## 7. Linux 调试工作流

### 统一排查顺序

1. 描述可重复的失败现象。
2. 找到最小复现输入和环境。
3. 查看现有日志，确认发生时间、线程、对象和请求标识。
4. 提出一个可以被数据支持或否定的假设。
5. 用 GDB、sanitizer、`strace`、`perf` 或 `/proc` 验证。
6. 修复最小根因。
7. 增加回归测试或故障注入点。
8. 写下结论和仍未知的部分。

### 工具用途

| 工具 | 主要回答的问题 |
|---|---|
| GDB | 程序停在哪里、调用栈是什么、变量和线程状态是什么 |
| ASan | 越界、use-after-free、部分泄漏 |
| UBSan | 整数溢出、空指针、非法转换等未定义行为 |
| TSan | 数据竞争和部分锁顺序问题 |
| `strace` | 程序进行了哪些系统调用，在哪里失败或阻塞 |
| `perf stat` | CPU 周期、缓存、上下文切换和分支等整体指标 |
| `perf record/report` | 热点函数和调用路径 |
| `/proc/<pid>/status` | 线程数、内存和状态 |
| `/proc/<pid>/fd` | 打开了哪些文件和套接字 |
| `lsof -p` | 文件描述符对应的资源 |
| `valgrind --tool=helgrind` | 某些并发问题，但不是首选 |

### 实操实验

#### 实验 1：文件打开失败

运行一个打开不存在文件的程序，用 `strace -e trace=openat,read,write,close` 观察失败系统调用和错误码。

#### 实验 2：文件描述符泄漏

写一个循环打开文件但不关闭的程序。通过 `/proc/<pid>/fd` 或 `lsof -p <pid>` 确认数量增长，再用 RAII 修复。

#### 实验 3：崩溃调用栈

制造一个空指针解引用或越界访问，在 Debug 构建下用 GDB 获取调用栈。记录：

- 崩溃信号。
- 出错函数。
- 关键局部变量。
- 修复后的回归测试。

#### 实验 4：阻塞与超时

让程序阻塞在不响应的套接字或管道上，用 `strace -p <pid>` 和 GDB 区分“死循环”“等待锁”“阻塞系统调用”。

#### 实验 5：性能基线

对同一个数据处理程序分别测量：

- 10 千条。
- 100 万条。
- 1000 万条记录。

记录耗时和峰值 RSS。不要只给绝对时间，应写清编译器、构建类型和测试命令。

## 8. 设备通信与协议

### 为什么一次读取不等于一条消息

串口和 TCP 都可能：

- 半包：一条消息分多次到达。
- 粘包：多条消息一次到达。
- 丢包或线路故障。
- 校验失败。
- 长度字段异常。

因此接收端必须使用增量解析器，而不是假设 `read()` 返回的正好是一帧。

### 推荐帧格式

项目练习使用以下格式：

```text
magic[2] = AA 55
version[1]
type[1]
sequence[2] little-endian
payload_length[2] little-endian
payload[payload_length]
crc16[2] little-endian
```

CRC16 计算范围从 `version` 到 `payload` 的最后一个字节。

### 解析器状态

```text
搜索头部 → 等待固定头 → 读取长度 → 检查长度上限
        → 等待完整载荷和校验 → 校验 → 产出 Frame
        → 失败：记录错误并从下一个字节重新搜索
```

### 必须处理的错误

- 垃圾字节。
- 错误 magic。
- 未知版本。
- 长度超过上限。
- 校验失败。
- 同一缓冲区内有多个完整帧。
- 帧被任意切分。
- 超时后主动断开。

### 重连策略

建议先采用确定性指数退避：

- 第一次 100 ms。
- 随后 200、400、800、1600、2000 ms。
- 最大间隔 2000 ms。
- 连接稳定一段时间后重置。

真实生产系统通常加入随机抖动，避免大量设备同时重连。项目 MVP 先实现确定性版本，方便测试。

## 9. 故障恢复与可观测性

### 设备状态机建议

```text
idle → connecting → online
                 ↘ degraded → online
任意未关闭状态 → closed
```

明确每个事件在哪个状态合法，非法事件应返回失败或记录诊断，而不是静默改变状态。

### 看门狗

看门狗不是“把整个进程杀掉并重启”这么简单。MVP 可先实现：

- 记录最后一次心跳时间。
- 周期任务检测超时。
- 超时后进入降级状态。
- 连续失败后尝试重连。
- 重连期间保留明确的旧状态处理策略。

### 指标

至少采集：

- 收到帧数、发送帧数。
- 校验错误数。
- 解析缓冲区当前大小。
- 队列当前长度和最大值。
- 普通任务和高优先级任务延迟。
- 重连次数。
- 最近一次心跳时间。

日志字段至少包含 `timestamp`、`thread`、`component`、`event`、`sequence` 和错误原因。
