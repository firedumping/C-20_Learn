# EdgeBot 旗舰项目

## 1. 项目定位

项目名称：**EdgeBot：端侧设备控制与可观测性终端**

项目的一句话描述：

> 基于 C++ 的单线程事件驱动服务，通过串口或虚拟传输连接设备，提供任务调度、优先级控制、协议解析、断线重连、故障注入和运行指标，后续可接入 OpenHarmony 界面与 ROS2 桥接。

这不是一个功能越多越好的机器人演示。面试价值来自以下问题是否处理完整：

- 系统为什么采用单线程事件循环。
- 关键任务如何越过普通任务。
- 设备数据如何分帧和校验。
- 过载、断线、损坏和异常回调如何恢复。
- 如何用日志和指标证明系统状态。
- 硬件、UI 和 ROS2 之间如何划清线程与所有权边界。

## 2. 范围控制

### MVP 必须包含

- Linux 下可运行的 C++20 服务。
- 单线程事件循环。
- 普通任务和高优先级任务。
- 有界任务队列。
- 定时器和超时。
- 虚拟设备传输。
- 增量帧解析和 CRC 校验。
- 连接状态机。
- 断线重连。
- 心跳检测。
- 结构化日志和基础指标。
- 自动化测试和故障注入。

### 第二阶段

- 通过真实 ESP32 或 STM32 连接传感器、按键和低压执行器。
- UART 或 CAN 通信。
- 真实断线、重启和线路干扰测试。

### 第三阶段

- 简单的 OpenHarmony 或 Linux UI。
- 显示连接状态、队列长度、最近故障和控制按钮。

### 第四阶段

- ROS2 桥接。
- Topic 发布设备状态。
- Service 或 Action 接收控制目标。
- 如果端侧环境不方便运行 ROS2，桥接层可以放在 Linux 网关。

### 明确不做

- SLAM、视觉识别和大模型推理。
- 复杂多窗口 UI。
- 完整机器人运动学。
- 为了炫耀技术而加入数据库、消息队列和微服务。
- 在 MVP 未通过之前接真实高压或高速电机。

## 4. 模块责任

### `event_loop`

负责：

- 投递普通任务。
- 投递高优先级任务。
- 执行当前批次任务。
- 执行到期定时器。
- 停止和关闭。
- 统计队列长度和执行数。

不负责：

- 直接读取串口。
- 直接更新 UI。
- 长期执行 CPU 密集计算。
- 拥有业务状态机。

### `transport`

负责：

- 打开、关闭和读写设备。
- 把底层错误转换为统一错误类型。
- 模拟断线和写失败。
- 记录收发字节数。

接口可以先用抽象基类：

```cpp
class Transport {
public:
    virtual ~Transport() = default;
    virtual std::size_t read(std::span<std::byte> output) = 0;
    virtual std::size_t write(std::span<const std::byte> input) = 0;
    virtual void close() = 0;
};
```

第一版同时实现：

- `VirtualTransport`：测试时注入数据。
- 后续 `SerialTransport`：真实串口。

不要让事件循环和业务状态机直接依赖 POSIX 串口 API。适配层是后续接 OpenHarmony 和 ISU 的关键边界。

### `frame_decoder`

负责：

- 累积字节。
- 搜索 magic。
- 解析长度和载荷。
- 检查最大长度。
- 校验 CRC。
- 产生 Frame 或错误。
- 从错误位置恢复。

该模块应是纯内存模块，不读取真实设备，便于自动测试和模糊测试。

### `device_session`

负责业务状态：

- 当前连接状态。
- 最近心跳时间。
- 重连次数。
- 命令序号。
- 状态迁移。

建议状态：

```text
idle
connecting
online
degraded
closed
```

示例事件：

```text
connect_requested
connection_opened
heartbeat_received
heartbeat_timeout
transport_error
close_requested
```

### `diagnostics`

负责：

- 结构化日志。
- 计数器、队列长度和延迟分布。
- 故障注入开关。
- 演示时导出的运行摘要。

日志字段至少包含：

```text
timestamp thread component event sequence queue_depth error_code
```

不要把每次高频事件都打印成完整日志，否则日志本身会改变性能。采用采样、聚合或调试级别控制。

## 5. 事件循环语义

项目采用以下明确语义：

1. 所有业务状态都由一个事件循环线程拥有。
2. `post` 只能在事件循环启动前或通过线程安全入口调用。
3. 从其他线程投递任务时，采用锁加条件变量通知，但不直接修改业务状态。
4. 一轮处理开始时，取出本轮就绪任务。
5. 回调中新投递的任务进入下一轮，减少无限重入。
6. 高优先级任务先于普通任务执行，同优先级保持 FIFO。
7. 队列有容量上限，满时返回 `full`。
8. 急停类任务不能因为普通任务过多而失败；可以预留给急停单独的高优先级容量。
9. 收到停止请求后不再接受新任务，但已完成排队的任务是否执行由关闭策略决定。
10. 每个任务异常必须被捕获，记录任务来源和异常，事件循环继续运行。

### 面试需要解释的取舍

- 为什么要保留单线程所有权？
- 如果外部线程为了投递任务加锁，是否又回到锁竞争？
- 为什么急停通道不能与普通任务共用全部容量？
- 为什么回调中新任务放到下一轮？
- 如果普通任务长期饥饿，怎样检测和处理？

## 6. 队列和过载策略

第一版采用“拒绝并上报”：

- 普通队列满时，返回 `full`。
- 调用者记录丢弃数量和错误码。
- 不阻塞事件循环线程。
- 不偷偷扩容。
- 不无限重试。

第二版可以增加：

- 普通任务允许丢弃最旧低优先级任务。
- 遥测数据按类型合并。
- 急停使用独立、预留的事件路径。

任何丢弃策略都必须可观测，并且有测试说明何时丢弃、谁负责上报。

## 7. 通信协议

### 帧格式

```text
offset  size  field
0       2     magic = 0xAA 0x55
2       1     version = 1
3       1     type
4       2     sequence, little-endian
6       2     payload_length, little-endian
8       N     payload
8+N     2     CRC16/CCITT-FALSE, little-endian
```

CRC 范围：从 `version` 到 payload 最后一个字节。

### 建议消息类型

| 类型 | 方向 | 作用 |
|---|---|---|
| 0x01 | 设备 → 端侧 | 心跳 |
| 0x02 | 设备 → 端侧 | 传感器数据 |
| 0x10 | 端侧 → 设备 | 控制命令 |
| 0x11 | 端侧 → 设备 | 急停 |
| 0x7F | 设备 → 端侧 | 错误报告 |

载荷长度限制建议从 256 字节开始。不要用无上限长度字段分配内存。

### 重连与超时参数

MVP 初始参数：

- 心跳间隔：500 ms。
- 心跳超时：1500 ms。
- 首次重连：100 ms。
- 最大重连间隔：2000 ms。
- 写超时：100 ms。

参数应集中配置，不能散落在业务代码里。

## 8. 分阶段任务与验收

### Milestone 0：建立基线

任务：

- 新建独立 CMake 项目。
- 建立 Debug 和 Release 构建。
- 开启高警告。
- 建立 CTest、ASan/UBSan。
- 写出架构图和状态机初稿。

验收：

- 空项目可以构建和运行。
- README 能说明当前阶段和未实现功能。
- 至少有一个自动测试。

### Milestone 1：事件循环核心

任务：

- 实现 `post`、`post_high_priority`、`run_once`、`request_stop`。
- 建立有界队列。
- 定义当前批次和回调重入语义。
- 加入任务异常隔离。

验收：

- 高优先级任务先执行。
- 同优先级保持 FIFO。
- 队列满返回明确结果。
- 停止后拒绝新任务。
- 回调抛异常不会摧毁事件循环。

### Milestone 2：定时器和心跳

任务：

- 定时器按截止时间执行。
- 相同截止时间保持投递顺序。
- 周期心跳任务。
- 超时后进入降级状态。

验收：

- 测试可控制时间，不依赖真实等待数秒。
- 超时只触发一次，恢复后重新计时。
- 长时间运行不会累积已完成定时器。

### Milestone 3：虚拟传输和协议

任务：

- 实现 `VirtualTransport`。
- 实现帧编码与增量解码。
- 支持半包、粘包和连续多帧。
- 支持 CRC 失败后重同步。
- 限制最大载荷。

验收：

- 同一帧在任意字节位置切开仍能解析。
- 一个缓冲区中的多个帧全部产出。
- 错误长度不会导致超大分配。
- CRC 错误有错误记录，后续正常帧仍可恢复。

### Milestone 4：设备状态、重连和看门狗

任务：

- 实现设备状态机。
- 实现指数退避。
- 实现连接失败、断线、心跳丢失和恢复。
- 定义关闭时资源释放。

验收：

- 非法状态事件被拒绝或记录。
- 重连间隔符合配置。
- 成功后退避重置。
- 关闭后不再注册定时器或投递业务任务。

### Milestone 5：诊断和故障注入

至少实现以下故障：

| 故障 | 注入方式 | 期望结果 |
|---|---|---|
| 半包 | 把一帧拆成多次输入 | 延迟产出，不崩溃 |
| 粘包 | 一次输入多帧 | 逐帧产出 |
| CRC 错误 | 修改载荷 | 记录错误并重同步 |
| 长度过大 | 构造超大长度 | 拒绝，不分配异常内存 |
| 断线 | 虚拟传输返回错误 | 进入降级并重连 |
| 队列满 | 连续投递任务 | 拒绝新任务并记录 |
| 心跳丢失 | 推进模拟时间 | 进入降级 |
| 回调异常 | 注入抛异常任务 | 记录并继续处理后续任务 |

完成指标：

- 帧发送数、接收数、CRC 错误数。
- 队列当前长度和最大长度。
- 普通任务和高优先级任务平均/尾部延迟。
- 重连次数。
- 最近心跳时间。
- 每个故障的发生次数。

### Milestone 6：真实硬件或 UI

二选一，不要同时拖延：

- 接 ESP32/STM32：证明真实串口或 CAN 链路。
- 接 OpenHarmony/Linux UI：证明窗口与端侧服务边界。

如果目标是 OpenHarmony 岗位，优先做 UI；如果目标是嵌入式岗位，优先接硬件。ROS2 桥接只在前两项稳定后再做。

## 9. 日志与排查记录

每次故障注入应记录：

```text
现象：
复现步骤：
初始假设：
使用的日志或工具：
根因：
修复：
回归测试：
仍存在的风险：
```

至少选一个真实问题写完整复盘。面试时，这份复盘比“项目功能列表”更有价值。

## 10. 性能测量

避免只展示程序“跑起来了”。至少测量：

1. 空事件循环投递并执行 10 万、100 万任务的耗时。
2. 普通任务与高优先级任务的调度延迟。
3. 1 万、10 万、100 万帧解析吞吐。
4. 半包和粘包场景下的解析正确性。
5. 队列满时的拒绝数量和内存变化。
6. Debug 与 Release 的差异。

记录方法：

```bash
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release
ctest --test-dir build-release --output-on-failure
perf stat ./build-release/edgebot_benchmark
```

如果使用 sanitizer：

```bash
cmake -S . -B build-asan \
  -DCMAKE_BUILD_TYPE=Debug \
  -DEDGEBOT_SANITIZE=address,undefined
cmake --build build-asan
ctest --test-dir build-asan --output-on-failure
```

TSan 与 ASan 一般分开构建，不要假设可以同时开启。

## 11. 演示流程

5～8 分钟演示建议：

1. 用一句话说明设备、端侧服务和观测工具的关系。
2. 正常运行：显示心跳、传感器帧和控制命令。
3. 高频输入：说明队列上限和背压。
4. 注入断线：展示降级、重连和恢复。
5. 注入 CRC 错误：展示错误计数和重新同步。
6. 注入回调阻塞：展示延迟指标以及如何定位。
7. 发送急停：展示高优先级路径。
8. 展示测试、sanitizer 和性能数据。
9. 解释一个失败方案及为什么改掉。

不要花大量时间介绍界面外观。

## 12. README 模板

项目 README 至少包含：

```markdown
# EdgeBot

## 项目目标
## 系统架构
## 构建与运行
## 事件循环语义
## 通信协议
## 状态机
## 过载和故障恢复
## 测试与故障注入
## 指标与性能数据
## 已知限制
## 下一阶段
```

“已知限制”不是弱点，而是证明你理解系统边界。例如：

- 当前虚拟传输未覆盖真实线路噪声。
- 当前只有 Linux 适配器。
- 当前重连没有随机抖动。
- 当前指标只保存在进程内。

这些限制必须和下一阶段计划对应。

## 13. 完成定义

一个可以用于投递的版本至少满足：

- 在 WSL2 中一条命令构建，一条命令运行测试。
- 事件循环、协议解析和状态机都有单元测试。
- 至少一个集成测试覆盖“断线—重连—恢复”。
- 至少一个 sanitizer 构建通过。
- 有可重复的故障注入命令。
- 有三项性能或运行指标。
- 有架构图和演示视频。
- 能解释至少一个没有采用的方案及原因。
