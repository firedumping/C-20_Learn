# 第 19 章：高级工程决策与能力地图

## 学习目标

本章不要求背更多 API，而是补齐做出工程决策所需的知识地图：

- 知道什么时候需要自定义分配策略或 `std::pmr`。
- 能区分运行时多态、模板和类型擦除的适用边界。
- 能从复杂度、分配和缓存行为评估标准容器与算法。
- 能设计有界并发系统，而不是无限创建线程。
- 能规划测试、性能、ABI 和依赖风险。
- 知道 C++20 中哪些较小特性值得在正确场景使用。

## 1. 分配与 `std::pmr`

普通容器默认通过全局分配器分配。频繁分配可能影响延迟、碎片和可预测性。C++17 引入的 polymorphic memory resources（PMR）允许运行时选择分配策略：

```cpp
#include <array>
#include <cstddef>
#include <memory_resource>
#include <vector>

void process() {
    alignas(std::max_align_t) std::array<std::byte, 4096> storage;
    std::pmr::monotonic_buffer_resource arena{
        storage.data(), storage.size()};

    std::pmr::vector<int> values{&arena};
    values.reserve(128);
}
```

这类 arena 适合生命周期短、批量创建、结束时统一释放的对象。它不适合：

- 单个对象需要长期独立释放。
- 不同对象生命周期交错。
- 未测量就替换默认分配器。

PMR 类型与普通类型不是同一类型，跨接口会传播容器别名。公开 API 前要想清楚是否真的需要。

## 2. 抽象工具的选择

同一需求有四种常见实现方式：

| 方式 | 决策时机 | 优点 | 代价 |
|---|---|---|---|
| 具体类型/组合 | 只有一种实现 | 简单、值语义 | 扩展需要改调用方 |
| 模板/Concepts | 类型集合在编译期已知 | 无运行时分派、可内联 | 模板实例和编译时间 |
| 虚函数 | 运行时插件或稳定接口 | 开放扩展、接口清晰 | 间接调用、生命周期管理 |
| 类型擦除（`std::function` 等） | 调用方不关心具体类型 | 值语义接口、可存异质对象 | 间接调用、可能分配 |

先从最具体方案开始。抽象不是越早越好；每层抽象都必须解决一个真实变化。

`std::function` 适合保存任意可调用对象，但可能分配，而且空状态需要检查。对只读、只是借用回调且生命周期受控的场合，项目可以实现更轻的非拥有函数视图；C++20 标准库没有通用 `function_ref`。

## 3. 算法、复杂度与缓存

复杂度不是全部性能。两个都是 O(n) 的算法可能因缓存局部性和分支预测差别巨大。

选择时同时考虑：

- 数据规模和增长方式。
- 主要操作：顺序遍历、随机访问、查找、插入、删除。
- 分配次数和对象大小。
- 引用/迭代器失效要求。
- 是否需要稳定顺序。
- 并发读写模式。

标准算法通常经过优化，但前提是正确使用：

```cpp
std::ranges::sort(values);
auto it = std::ranges::lower_bound(values, target);
```

`lower_bound` 要求有序。输入是否有序、比较器是否满足严格弱序，是调用者必须保证的合同。

不要用 `std::list` 仅仅因为“中间插入 O(1)”。移动到插入位置本身可能 O(n)，链表节点分散还会破坏缓存。默认从 `std::vector` 开始并用数据验证。

## 4. 有界并发

`thread` 是操作系统线程资源。请求数增长时直接创建新线程会耗尽资源：

```text
每请求一线程 -> 线程创建/调度/栈内存成本 -> 延迟抖动 -> 拒绝服务
```

更可控的架构是线程池或固定数量 worker：

```text
producer(s) -> bounded queue -> fixed worker pool -> result queue
```

需要明确：

- 队列是否有界，满了以后阻塞、拒绝还是丢任务？
- 关闭时是否处理完剩余任务？
- 异常如何传回调用者？
- 任务能否取消？
- 哪个线程拥有结果？
- 队列、锁和条件变量的退出条件是什么？

无限队列只是把过载从线程数量转移为内存增长，不是真正背压。

### 伪共享

不同线程修改相邻但独立的变量，仍可能竞争同一缓存行：

```cpp
struct WorkerState {
    alignas(64) std::uint64_t processed;
    char padding[64];
};
```

对齐只是候选修复，必须验证缓存行大小和真实性能。过度对齐可能增加内存和分配压力。

### 内存序

默认 `memory_order_seq_cst` 最容易推理。更弱的内存序只能在你能写出 happens-before 证明时使用：

- `relaxed`：只保证该原子对象操作不可分割，不建立跨对象发布关系。
- `acquire` / `release`：常见于发布初始化和读取初始化数据。
- `acq_rel`：读改写操作同时需要两侧关系。

数据竞争仍是未定义行为。原子操作不能自动让一组字段成为一个事务。

## 5. 测试进阶

除了示例驱动测试，还应考虑：

### 属性测试

定义对所有合法输入都应成立的性质：

```text
encode(decode(bytes)) == bytes         （规范编码）
sum(split(sequence)) == sum(sequence)
parse(format(value)) == value
```

### 模糊测试

把解析器暴露给随机或变异输入，重点检查崩溃、越界、无限循环和超量分配。日志分析器、二进制读取器和命令行参数都是适合的目标。

### 并发测试

并发测试不能只“多跑几遍”。需要：

- ThreadSanitizer（工具链支持时）。
- 明确共享状态和不变量。
- 可重复的停止/关闭测试。
- 压力测试与超时。
- 专门的锁顺序和队列边界测试。

### 故障注入

在测试替身中让文件打开失败、写入中断、分配失败或回调抛异常，验证资源释放和对象状态。

## 6. 性能工作流

不要从“把函数写成一行”开始优化。按顺序：

1. 写正确、可读的版本。
2. 定义指标：吞吐、p99 延迟、峰值 RSS、分配次数。
3. 建立固定输入和环境。
4. 记录基线。
5. 使用 profiler 找热点。
6. 每次只改一个因素。
7. 记录收益、回归和可维护性代价。

基准测试要防止编译器删除未使用结果，并避免把 I/O、首次分配和缓存预热混入不该测的部分。不同机器的绝对时间不能直接比较，应比较同一环境的相对变化。

## 7. C++20 小特性速查

以下特性通常在特定场景很有价值，但不应为了使用而使用：

| 特性 | 适用场景 | 注意 |
|---|---|---|
| `char8_t` | 明确 UTF-8 数据 | 与 `char` 字符串互操作需要转换 |
| `using enum` | 简化枚举成员书写 | 控制暴露范围 |
| 模板 lambda | 泛型局部算法 | 模板实例可能增加编译成本 |
| `[[likely]]` / `[[unlikely]]` | profiler 验证后的热点分支 | 猜错可能降低性能 |
| `[[no_unique_address]]` | 空状态成员优化 | ABI 和布局依赖实现 |
| `std::to_address` | 泛型迭代器/指针抽象 | 不替代所有权设计 |
| `std::assume_aligned` | 已知底层地址对齐的热点 | 前提错误导致未定义行为 |
| `std::is_constant_evaluated` | 编译期分支 | 不要用它制造语义分叉 |
| `std::bit_cast` | 同大小平凡类型间位复制 | 不处理字节序 |
| `std::source_location` | 日志、断言诊断 | 不要保存过期临时上下文 |
| `std::atomic_ref` | 现有对象临时原子访问 | 生命周期和所有访问规则必须一致 |
| `std::construct_at` / `destroy_at` | 低层容器与对象生命周期 | 需要精确构造/析构责任 |

## 8. 依赖与发布

选用第三方库时检查：

- 许可证是否允许当前分发方式。
- C++ 标准和 ABI 要求。
- 维护频率、安全响应和测试质量。
- 是否必须修改全局编译选项。
- 静态链接/动态链接的传播要求。
- 平台和架构支持。

把第三方库隔离在适配层中，避免领域代码到处依赖其类型。这样替换实现、补测试和限制异常边界更容易。

## 9. 从练习到真实项目

建议的项目迭代：

1. 先写输入/输出合同和失败语义。
2. 写纯领域函数和测试。
3. 加入文件/网络适配器。
4. 加入诊断和错误码。
5. 加入 sanitizer、profiler 和基准。
6. 再根据测量决定是否并发、缓存或更换数据结构。
7. 最后考虑 ABI、模块化和发布。

## 练习 1：设计并发批处理器

设计一个有界任务系统：

- 固定 worker 数量。
- 有界队列和背压。
- 支持正常关闭。
- 任务异常可回传。
- 处理完或明确拒绝后返回退出码。

先画状态机，再写代码。不要用无界队列隐藏过载。

## 练习 2：为日志项目做一轮性能审查

对 `projects/log_analyzer`：

- 生成 10 万、100 万、1000 万行合成数据。
- 记录耗时、峰值内存和分配次数。
- 比较 `map` 与 `unordered_map` 的聚合性能。
- 输出顺序仍需稳定，或在性能测试中明确不比较顺序。
- 只在 profiler 指向热点时修改解析代码。

## 练习 3：C++20 特性选型

对以下需求判断是否使用模板、虚函数、`std::variant`、`std::function` 或具体类型：

1. 两种形状只在编译期使用。
2. 插件在运行时通过共享库加载。
3. 固定集合的三种消息。
4. 保存任意用户回调，可能为空。
5. 只有一个日志格式化器实现。

写出选择、成本和替代方案。
